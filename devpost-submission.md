## Devpost write-up

## Inspiration

Choosing clothes involves both imagining a look and remembering which pieces deserve another visit. A garment photo captures the item, but it does not show how that look might appear on the shopper. StoreTryOn brings those two views together in a SPECS Lens: a photo-based appearance preview and a small shopping list of the pieces worth returning to.

## What it does

StoreTryOn guides the shopper through **Your photo → Garment → Review → Try-on → Saved piece**. The shopper chooses a front-facing full-body photo once per visit, then selects Shirt or Jacket and reviews a garment photo. Only the explicit **Try it on** action sends the two images for generation.

The result page shows the garment beside its generated preview and identifies the source. **Add to shopping list** saves the pair as local JPEG thumbnails. A second Add cannot duplicate the same result. The shopper can try another garment using the same shopper photo, browse photo cards, and reopen both images. Clearing the list requires confirmation; a full list reports the problem without silently removing earlier entries.

The current demo is actual **Lens Studio · SPECS preview** footage with labelled synthetic input photos. Its **Generated by YouCam** result comes from a real API request. The separately selected illustration mode is labelled and makes no API request.

## How it was built

The Lens is written in TypeScript in Lens Studio, using Spectacles UIKit for its guided spatial window and Spectacles Interaction Kit for native hand controls. The hardware capture path uses SPECS `CameraModule`. Its intended shopper-photo step photographs an existing full-body image displayed on another screen or print, then reuses that image during the visit; it does not assume a glasses selfie camera. The editor uses a labelled synthetic input source so the flow can be exercised without claiming camera evidence.

YouCam **AI Clothes V4** powers the generated appearance: shirts use `upper_body`, while jackets use `outer`, which layers outerwear over the existing outfit. The Lens uses native `InternetModule` HTTPS requests to a protected Node.js proxy. That server registers and uploads both image files, creates the Clothes V4 task, polls for completion, and downloads the result bytes. The Lens decodes those bytes and encodes local JPEG thumbnails when saving.

The YouCam provider API key stays on the server. The Lens uses a separate revocable prototype access token, with bounded requests, jobs and result lifetimes and sanitized errors. This token is not a production identity system. Saved entries contain image bytes rather than expiring provider links. Clearing the local list removes its local entries; it does not claim deletion of provider-held images.

Codex helped implement and review the native flow, proxy, storage guards and LEAF scenarios; diagnose interrupted response handling; inspect actual preview behavior; and produce the Remotion demo from recorded successful footage. Runtime checks and real provider responses were used to distinguish working behavior from simulation.

## Challenges

A real request exposed a failure that a compile check could not catch: a polling response returned HTTP 200, then its connection closed while the body was being read. The client now retries bounded read-only GETs, retains the known job and completed bytes for recovery, and never automatically repeats the paid creation POST. Native decoding must accept the returned image before that recovery state is released.

Spatial interaction also exposed lifecycle timing: rebuilding a page during SIK hover release could stall a test. Queuing page actions across late-update frames resolved that race. Storage required similar care: bounded JPEG saves, duplicate prevention, explicit clear confirmation and preservation of existing entries when a save fails.

## Accomplishments

The redesigned guided UI completed a real YouCam shirt request through the normal visible hand controls, decoded a **1024 × 1536** image, saved exactly one garment/result pair, and opened its collection and detail views. The recorded processing wait is retained at actual speed in the 1:54 demo.

Separate real adapter calls also succeeded for both `upper_body` and `outer` using synthetic inputs. Preview scenarios cover both categories, shopper-photo reuse, retake and Back, background generation, recovery, storage capacity, duplicate prevention, scrolling, clear confirmation, and image-byte persistence across preview resets. Eleven backend tests use mocked provider transport and local HTTP; those tests are not presented as live API evidence.

## What was learned

A try-on experience needs more than a generated image. The user must understand which photos will be sent, whether the result is live or illustrative, what is happening during the wait, and whether a save really succeeded. Keeping recovery tied to one known job matters when a network interruption could otherwise encourage another paid attempt. Persisting actual thumbnails also makes the shopping list independent of a temporary result URL.

Verification has to follow the full path: native controls, HTTPS transport, provider processing, image decoding, save, and reopen. Editor preview can establish much of that path, while physical camera behavior and wearable usability require their own tests.

## What is next

The next milestone is physical SPECS validation: real shopper and garment photos, in-store lighting, networking, hand tracking, readability, comfort, and persistence across device sessions. A broader release also needs user authentication, abuse controls, a clearer personal-photo retention experience, and accessible judge distribution.

StoreTryOn is a working editor-preview prototype, not a production service or a fit-measurement tool. Generated appearance can help compare a look; shoppers still need to check physical fit in store.

## Testing instructions

1. Open `StoreTryOn.esproj` in Lens Studio 5.23.2 or newer with the bundled compatible SIK 2.0.0, UIKit 2.0.0 and LEAF 2.0.2 packages; use SPECS preview.
2. Load the labelled sample shopper photo, review it, and select **Use this photo**. Choose Shirt or Jacket, load its garment photo, and review it.
3. For the live path, configure the protected proxy and a separate local prototype credential using the project setup instructions. **Try it on** sends photos to YouCam and uses credits. Startup, loading photos and browsing do not generate. Keep the provider API key out of the Lens and project assets.
4. Inspect the **Generated by YouCam** result, add it once, open the shopping list and saved piece, and try another garment with the same shopper photo. Test Keep items and Clear list separately.
5. For a free UI check, explicitly choose **Use illustrations** in editor-only Preview settings. Its output is labelled as illustrative and does not verify the API.

Source access and local proxy setup are required on a new machine. The private repository and prototype credential are not a public instant-play demo. Physical-device tests remain outstanding. See README.md and devpost/ui-ux-verification.md for setup and exact evidence boundaries.
